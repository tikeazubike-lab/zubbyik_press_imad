## 2. §2 item 3 — honeypot re-test: exposed a DEEPER, PRE-EXISTING BUG

I went to re-test the discovery form's honeypot on production as instructed.
It failed — but not for the reason §5.3 predicted, and not because the fix
was missing. The discovery form is **completely non-functional** and always
has been.

### Raw evidence (production, before any new fix)

**Test A — honeypot filled:**
```
Security check failed. Please refresh and try again.
```

**Test B — honeypot empty (control):**
```
Security check failed. Please refresh and try again.
```

Both fail identically, *before* the honeypot is even evaluated. So the
honeypot was never the reason.

### Root cause

The handler's nonce check runs before the honeypot check:

```php
// contact-handler.php
if ( ! isset( $data['malachy_nonce'] ) || ! wp_verify_nonce( $data['malachy_nonce'], 'malachy_contact_nonce' ) ) {
    return new WP_Error( 'invalid_nonce', 'Security check failed...' );
}
```

But the discovery form posts a nonce field named **`discovery_nonce`**:

```php
// section-hero.php (discovery form)
<?php wp_nonce_field( 'malachy_contact_nonce', 'discovery_nonce' ); ?>
```

`$data['malachy_nonce']` is never set for that form → the check fails on
every submission.

### Confirmed pre-existing (git history)

```
$ git log -S"discovery_nonce" -- section-hero.php
2b0b0ce feat: discovery call panel, offers redesign with icon...

$ git log -S"malachy_nonce" -- contact-handler.php
a9c8639 initial commit imadconsulting portfolio
```

The discovery panel was added in `2b0b0ce`; the handler has checked
`malachy_nonce` since the initial commit. **The two names have never
matched — the discovery form has never successfully submitted anything.**

### Implication for §5.3

§5.3's honeypot regression was real in code, but **moot in effect**: the
nonce check failed first, so the honeypot was never reached. The honest
description is not "honeypot unprotected" — it is **"the form never worked
at all."**

### Fix written (commit `f1eca1f`, version `1.3.13`) — NOT yet on production

- `contact-handler.php`: accept **either** nonce field name
  (`malachy_nonce` or `discovery_nonce`), so cached markup still posting the
  old name also verifies.
- `section-hero.php`: renamed the discovery form's nonce field to
  `malachy_nonce` for consistency.

**Verified on staging:**

```
honeypot FILLED -> "Thank you! Your message has been sent."   (fake success = caught)
honeypot EMPTY  -> "Could not send message. Please try again later."
                   (nonce now PASSES, honeypot passes, reaches wp_mail;
                    wp_mail returns false on staging — no mail transport, pre-existing env limit)
nonce field     -> "malachy_nonce"
main contact form -> "Thanks! I'll get back to you soon." (no regression from the nonce change)
```

**Status: fix written, not yet live.** Production still serves `1.3.12`; the
discovery form remains broken there until `f1eca1f` is pulled + Cloudflare
purged, after which the honeypot re-test can actually be run.

## 4. §3 — spam-window check: nothing could have gotten through

The discovery form does **not** persist submissions anywhere (it only posts
to WordPress `admin-ajax` → `wp_mail`; there is no DB row, unlike the main
contact form which goes to the backend). So there is no submission log to
audit.

More importantly: because the nonce check failed on **every** submission
since `2b0b0ce`, the form **never sent a single email** — spam or otherwise.
There is no unprotected window to clean up; the form rejected 100% of
submissions outright.

Checked:
```
leads table: 8 rows, all from the main contact form / chatbot
             (discovery submissions never reach the backend DB)
WP debug.log: no contact/honeypot/nonce entries
```

**Conclusion: no cleanup required beyond the code fix.**

## 5. §4 — lessons recorded

Both recorded as requested, and both directly applicable here:

1. **Shared handlers need every caller checked, not just the one being
   changed.** §5.3's root cause. The nonce field mismatch is a second,
   sharper instance of the same failure mode: a shared handler whose
   contract was only ever validated against one of its two callers. The
   fix now accepts either field name rather than assuming one.
2. **"Deployed to production" must be its own tracked step.** §5.1's root
   cause. Staging verification was honest but production promotion was
   assumed. Going forward, every change gets an explicit
   "deployed + re-verified on production" step.
