## 5. Addendum — post-sign-off findings and fixes

Added 2026-09-22 after Malachy tested the campaign link on production and
reported the hero button was not changing. Four issues surfaced; all fixed.

### 5.1 Production was running pre-integration code (confirmed, then resolved)

**Symptom:** the `/r/status` campaign link redirected to production correctly,
but the hero button did not swap and there was no Contact flow change.

**Diagnosis (live, raw):**

| Check | Production (then) | Repo (correct) |
|---|---|---|
| Hero button with `?utm_source` | `View My Projects` (no swap) | `Tell me your problem` |
| Contact form label | `What can I help with?` | `What are you trying to solve?` |
| Honeypot field | `malachy_hp` | `website` |
| `source_campaign` field | missing | present |
| `contact.js` version | `?ver=1.3.9` | — |

Production's server-rendered HTML contained the *old* markup, so this was not
a cache artefact — production simply had not been deployed since the
integration commit `4524cde`.

**Environment note (asked and answered):** it was **not** a staging-vs-prod
behaviour difference — both render identically at the same viewport. It was a
deployment gap only: staging is the VPS (bind-mounted theme, always current);
production is Cloudflare-proxied with a shared-host origin, updated by
`git pull`.

**Resolution:** production pulled `main`; re-verified live, now serving
`?ver=1.3.10` with the correct markup.

### 5.2 Integration commit never bumped the theme version (fixed)

Commit `4524cde` changed `contact.js` and `section-contact.php` but left
`MALACHY_THEME_VERSION` at `1.3.9`. Even after a deploy, assets would still be
requested at `?ver=1.3.9` and served from browser/CDN cache — the new
`contact.js` (hero swap + dual submit) would be invisible.

**Fix:** bumped to `1.3.10` (commit `d929958`) so the asset URL changes and
caches are bypassed.

### 5.3 Discovery-panel honeypot silently disabled (fixed)

Renaming the main contact form's honeypot `malachy_hp` → `website` (to match
the backend schema) also changed the shared handler to check **only**
`website`. The slide-out **"Book a Discovery Call"** panel form still posts
`malachy_hp`, so its honeypot had silently stopped being checked.

**Fix (commit `cb4ec7e`):** handler now rejects if **either** field is
non-empty, protecting both forms:

```php
if ( ! empty( $data['website'] ) || ! empty( $data['malachy_hp'] ) ) {
```

### 5.4 Hero CTAs below the fold on short desktop viewports (fixed)

**Symptom:** both hero CTA buttons were below the visible area on Malachy's
Windows desktop.

**Diagnosis (measured, both sites identical):** the hero's natural content
height is **~672px** (100px top padding + ~570px content) and did not
compress. On viewports under ~602px tall the buttons fell below the fold:

| Viewport height | Buttons bottom | Visible |
|---|---|---|
| 640–900 | ≤ 601 | yes |
| 600 | 602 | no |
| 560–440 | ~604 | no |

Cause: small laptop screens, non-maximised windows, or ~125% browser zoom.

**Fix (commit `c979827`, version `1.3.12`):** two desktop-only tiers:

```css
@media (min-width: 801px) and (max-height: 720px) { /* tighter padding/title/margins */ }
@media (min-width: 801px) and (max-height: 520px) { /* further compression */ }
```

**Verified after fix:**

| Viewport height | CTA visible |
|---|---|
| 900 / 800 / 720 / 700 / 640 / 600 / 560 / 520 / 480 / 440 | ✅ |
| 400 | ❌ (extreme; content min ~422px) |

Normal desktop (≥721px tall) is unchanged — buttons at 677–720 vs the
678–721 baseline. Mobile (≤800px) layout untouched.
