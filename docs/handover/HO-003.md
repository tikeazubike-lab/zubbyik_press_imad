## 1. Problem Statement

HO-002 shipped a two-tier router:

```
Tier 0 (Static cache, 12 keyword patterns) ──miss──► Tier 2 (LLM, mimo-v2.5)
```

The portfolio's structured content — 8 skills, 3 projects, 4 experience entries, 5 blog posts, all already fetched and cached in `malachy_chat_context` — is only ever used as a system-prompt blob handed to the LLM. It is never queried directly. Result: any question that doesn't match one of the 12 fixed phrases (e.g. *"have you done DNS hardening?"*, *"what's a QA project you've shipped?"*, *"tell me about your SPF/DKIM experience"*) falls straight through to the LLM — even though the answer is a literal field on a CPT row already sitting in memory.

This costs latency + token spend (Section 18 of HO-002) on questions that are actually deterministic lookups, and it means editing a Project/Skill CPT only changes what the LLM *might* say, never what the bot *reliably* says.

## 2. Fix

Insert a new **Tier 1 — Knowledge Retrieval** stage between the static cache and the LLM:

```
Tier 0 — Static conversational cache (unchanged: greetings, hire, pricing, meta)
    │ no match
    ▼
Tier 1 — Structured CPT retrieval (NEW: score message against skills/projects/
          experience/posts already in malachy_chat_context, template a reply
          from the winning item)
    │ score below threshold
    ▼
Tier 2 — LLM fallback (unchanged endpoint/model, but now receives the Tier 1
          near-miss as a grounding hint instead of nothing)
```

No vector DB, no embeddings, no new dependency — the corpus is ~20 items, so a plain tokenized keyword-overlap score is sufficient and keeps the "vanilla JS/PHP, no build step" constraint from HO-002 Section 17 intact.

## 4. Implementation

### 4.1 Tokenizer + synonym expansion

```php
/**
 * Lowercase, strip punctuation, split on whitespace, drop stopwords,
 * then expand each token through a small hand-authored synonym map so
 * that domain phrasing ("CI/CD", "pipeline", "automation") converges
 * on shared tokens without needing real NLP/embeddings.
 */
private function tokenize( string $text ): array {
    $text = strtolower( $text );
    $text = preg_replace( '/[^\p{L}\p{N}\s\/]/u', ' ', $text ); // keep slashes for "CI/CD", "SPF/DKIM"
    $raw_tokens = preg_split( '/[\s\/]+/', trim( $text ), -1, PREG_SPLIT_NO_EMPTY );

    $stopwords = [ 'a','an','the','is','are','do','does','you','your','have',
        'has','i','me','my','what','which','tell','about','can','could','would',
        'of','on','in','to','for','with','and','or','it','that','this' ];

    $tokens = array_diff( $raw_tokens, $stopwords );

    return $this->expand_synonyms( $tokens );
}

/**
 * Domain synonym groups — extend this list as Tier-1 near-miss logs
 * (Section 6) surface real visitor phrasing that isn't converging yet.
 */
private function expand_synonyms( array $tokens ): array {
    static $synonym_groups = [
        [ 'dns', 'spf', 'dkim', 'dmarc', 'email', 'deliverability', 'spam', 'authentication' ],
        [ 'ci', 'cd', 'cicd', 'pipeline', 'automation', 'automate', 'devops', 'workflow' ],
        [ 'wordpress', 'wp', 'theme', 'plugin', 'cms' ],
        [ 'qa', 'test', 'testing', 'quality', 'assurance', 'bug', 'regression' ],
        [ 'infra', 'infrastructure', 'sysadmin', 'server', 'vps', 'docker', 'container', 'containerization' ],
        [ 'project', 'built', 'build', 'shipped', 'sample', 'showcase', 'case', 'study', 'portfolio' ],
        [ 'llm', 'ai', 'chatbot', 'chat', 'bot', 'assistant', 'artificial', 'intelligence' ],
    ];

    $expanded = $tokens;
    foreach ( $synonym_groups as $group ) {
        if ( array_intersect( $tokens, $group ) ) {
            $expanded = array_merge( $expanded, $group );
        }
    }
    return array_unique( $expanded );
}
```

### 4.2 Build a scoreable index from the existing context cache

This piggybacks on `malachy_chat_context` (HO-002 Section 5) — same 1-hour TTL, same invalidation-on-CPT-save hook. No separate cache lifecycle to maintain.

```php
/**
 * Flatten the cached portfolio context (skills/projects/experience/posts)
 * into a uniform, scoreable candidate list. Cached alongside
 * malachy_chat_context under its own key so this flattening/tokenizing
 * work isn't repeated on every request.
 */
private function build_knowledge_index( array $context ): array {
    $cached = get_transient( 'malachy_chat_knowledge_index' );
    if ( $cached !== false ) {
        return $cached;
    }

    $index = [];

    foreach ( $context['skills'] ?? [] as $skill ) {
        $blob = $skill['title'] . ' ' . $skill['description'];
        $index[] = [
            'type'     => 'skill',
            'payload'  => $skill,
            'keywords' => $this->tokenize( $blob ),
        ];
    }

    foreach ( $context['projects'] ?? [] as $project ) {
        $tech = implode( ' ', $project['tech_stack'] ?? [] );
        $blob = $project['title'] . ' ' . $project['description'] . ' ' . $tech;
        $index[] = [
            'type'     => 'project',
            'payload'  => $project,
            'keywords' => $this->tokenize( $blob ),
        ];
    }

    foreach ( $context['experience'] ?? [] as $exp ) {
        $blob = $exp['title'] . ' ' . ( $exp['company'] ?? '' ) . ' ' . ( $exp['description'] ?? '' );
        $index[] = [
            'type'     => 'experience',
            'payload'  => $exp,
            'keywords' => $this->tokenize( $blob ),
        ];
    }

    foreach ( $context['posts'] ?? [] as $post ) {
        $blob = $post['title'] . ' ' . $post['excerpt'];
        $index[] = [
            'type'     => 'post',
            'payload'  => $post,
            'keywords' => $this->tokenize( $blob ),
        ];
    }

    // Same 1hr TTL as malachy_chat_context — invalidated by the same
    // CPT-save hook already wired in HO-002 (extend that hook to also
    // delete_transient('malachy_chat_knowledge_index')).
    set_transient( 'malachy_chat_knowledge_index', $index, HOUR_IN_SECONDS );

    return $index;
}
```

**Required one-line change to the existing CPT-save invalidation hook** (wherever HO-002 clears `malachy_chat_context` on save):

```php
delete_transient( 'malachy_chat_context' );
delete_transient( 'malachy_chat_knowledge_index' ); // NEW — keep in sync
```

### 4.3 Scoring — Tier 1 match

```php
/**
 * Tier 1: score the incoming message against the knowledge index built
 * in 4.2. Returns the best match + score, or null if nothing clears
 * the confidence threshold (falls through to Tier 2/LLM).
 */
private function get_knowledge_match( string $message, array $context ): ?array {
    $tokens = $this->tokenize( $message );
    if ( empty( $tokens ) ) {
        return null;
    }

    $index = $this->build_knowledge_index( $context );

    $best = null;
    $best_score = 0.0;

    foreach ( $index as $candidate ) {
        if ( empty( $candidate['keywords'] ) ) {
            continue;
        }
        $overlap = count( array_intersect( $tokens, $candidate['keywords'] ) );
        if ( $overlap === 0 ) {
            continue;
        }
        // Overlap ratio against the SHORTER of the two token sets —
        // prevents long project descriptions from being unfairly hard
        // to match against short visitor questions.
        $denominator = min( count( $tokens ), count( $candidate['keywords'] ) );
        $score = $overlap / max( $denominator, 1 );

        if ( $score > $best_score ) {
            $best_score = $score;
            $best = $candidate;
        }
    }

    // Threshold — start at 0.35. Tune using the near-miss log (Section 6)
    // after 1-2 weeks of real traffic rather than guessing further.
    $threshold = apply_filters( 'malachy_chat_tier1_threshold', 0.35 );

    if ( $best !== null ) {
        $this->log_nearmiss( $message, $best['type'], $best_score, $best_score >= $threshold );
    }

    if ( $best !== null && $best_score >= $threshold ) {
        return [ 'match' => $best, 'score' => $best_score ];
    }

    return null;
}
```

### 4.4 Reply templating per content type

```php
/**
 * Turn a winning Tier 1 candidate into a first-person reply, matching
 * the voice rule from HO-002 Section 5 (system prompt: first person,
 * never third person).
 */
private function compose_reply_from_match( array $candidate ): string {
    $item = $candidate['payload'];

    switch ( $candidate['type'] ) {
        case 'skill':
            return sprintf(
                "Yes — **%s** is one of my core skills. %s",
                esc_html( $item['title'] ),
                esc_html( $item['description'] )
            );

        case 'project':
            $tech = ! empty( $item['tech_stack'] )
                ? ' Built with ' . implode( ', ', array_map( 'esc_html', $item['tech_stack'] ) ) . '.'
                : '';
            return sprintf(
                "One example is **%s**: %s%s",
                esc_html( $item['title'] ),
                esc_html( $item['description'] ),
                $tech
            );

        case 'experience':
            return sprintf(
                "That's from my time as **%s** at %s (%s). %s",
                esc_html( $item['title'] ),
                esc_html( $item['company'] ?? '' ),
                esc_html( $item['duration'] ?? '' ),
                esc_html( $item['description'] ?? '' )
            );

        case 'post':
            return sprintf(
                "I've actually written about this — **%s**. %s",
                esc_html( $item['title'] ),
                esc_html( $item['excerpt'] )
            );

        default:
            return '';
    }
}
```

### 4.5 Follow-up resolution ("tell me more about that")

HO-002's routing has no concept of conversational continuity — every message is scored independently against `history` only inside the LLM's system prompt, never against the Tier 0/1 layers. Add a lightweight follow-up check ahead of Tier 1 proper:

```php
/**
 * If this message looks like a follow-up ("tell me more", "and that
 * one?", "why?") and the previous turn was a Tier 1 match, re-run
 * compose_reply_from_match() against a DEEPER field (e.g. project's
 * full case-study body instead of description) rather than falling
 * through to the LLM or re-matching from scratch.
 */
private function get_followup_match( string $message, array $history ): ?array {
    $followup_patterns = [ 'tell me more', 'more about that', 'go on', 'and that', 'why', 'how so', 'elaborate' ];
    $normalized = strtolower( trim( $message ) );

    $is_followup = false;
    foreach ( $followup_patterns as $pattern ) {
        if ( str_contains( $normalized, $pattern ) ) {
            $is_followup = true;
            break;
        }
    }
    if ( ! $is_followup || empty( $history ) ) {
        return null;
    }

    $last_source = end( $history )['_tier1_type'] ?? null;
    $last_payload = end( $history )['_tier1_payload'] ?? null;
    if ( ! $last_source || ! $last_payload ) {
        return null; // last turn wasn't a Tier 1 hit — let LLM handle continuity via its own history param
    }

    return [ 'type' => $last_source, 'payload' => $last_payload ];
}
```

**Note:** this requires the JS to echo back `_tier1_type`/`_tier1_payload` in the `history` array it already sends (HO-002 Section 15 request body). This is the one small JS-side change — the JS just needs to store whatever the PHP response tags each turn with and pass it back verbatim, no logic needed client-side.

### 4.6 Wire into the router

Replace the existing static→LLM jump in `handle_chat_request()`:

```php
// Tier 0 — unchanged from HO-002
$static = $this->get_static_answer( $message );
if ( $static !== null ) {
    return [ 'reply' => $static, 'source' => 'static' ];
}

// NEW — follow-up check, ahead of fresh Tier 1 scoring
$followup = $this->get_followup_match( $message, $history );
if ( $followup !== null ) {
    return [
        'reply'  => $this->compose_reply_from_match( $followup ),
        'source' => 'knowledge_followup',
        '_tier1_type'    => $followup['type'],
        '_tier1_payload' => $followup['payload'],
    ];
}

// NEW — Tier 1
$context = $this->get_portfolio_context(); // existing HO-002 method, cached
$knowledge = $this->get_knowledge_match( $message, $context );
if ( $knowledge !== null ) {
    return [
        'reply'  => $this->compose_reply_from_match( $knowledge['match'] ),
        'source' => 'knowledge',
        'score'  => $knowledge['score'],
        '_tier1_type'    => $knowledge['match']['type'],
        '_tier1_payload' => $knowledge['match']['payload'],
    ];
}

// Tier 2 — LLM, unchanged endpoint/model/system-prompt from HO-002,
// but now grounded with the closest Tier 1 candidate as a hint even
// though it didn't clear the threshold (Section 5).
return $this->call_llm( $message, $history, $context, $best_nearmiss ?? null );
```

## 5. Grounding the LLM fallback with near-misses

Even when nothing clears the 0.35 threshold, the *closest* candidate is still useful context — it stops the LLM from inventing details when the honest answer is "I don't have a specific example of that, but here's what's adjacent." Modify the LLM system prompt construction (HO-002 Section 5) to append, when available:

```php
if ( $best_nearmiss !== null ) {
    $hint = sprintf(
        "\n\nNote: the closest matching portfolio item to the visitor's question is '%s' (%s), though it wasn't a strong enough match to answer directly — use it only if genuinely relevant, otherwise answer normally.",
        $best_nearmiss['payload']['title'] ?? '',
        $best_nearmiss['type']
    );
    $system_prompt .= $hint;
}
```

## 6. Near-miss logging (closes the loop)

This is the mechanism that lets Tier 1 improve over time without guesswork, and it directly extends the "Analytics tracking" item already on your Future Enhancements backlog (HO-002 Section 19).

```php
/**
 * Log every Tier 1 attempt (hit or miss) to a capped wp_option array.
 * No new DB table — this traffic volume doesn't warrant one, and it
 * keeps the "no new infra" footprint HO-002 established.
 */
private function log_nearmiss( string $message, string $type, float $score, bool $hit ): void {
    $log = get_option( 'malachy_chat_nearmiss_log', [] );

    $log[] = [
        'message' => mb_substr( sanitize_text_field( $message ), 0, 200 ),
        'type'    => $type,
        'score'   => round( $score, 3 ),
        'hit'     => $hit,
        'time'    => current_time( 'mysql' ),
    ];

    // Cap at 500 entries, drop oldest — this is a tuning log, not an audit trail
    if ( count( $log ) > 500 ) {
        $log = array_slice( $log, -500 );
    }

    update_option( 'malachy_chat_nearmiss_log', $log, false ); // false = don't autoload
}
```

Review this log after 1–2 weeks of real traffic:
- Entries with `hit: false` and `score` between ~0.15–0.34 are your best signal for **new synonym-group entries** in `expand_synonyms()`.
- Entries with `hit: false` and `score` near 0 across many different `message` values with a shared theme are candidates for a **new Tier 0 static pattern** (fixed, high-value phrasing) rather than Tier 1.
- If a specific `type` (e.g. `experience`) never hits, its keyword blob in `build_knowledge_index()` may need richer source content in the CPT itself.

No admin UI needed initially — this is inspectable via WP-CLI (`wp option get malachy_chat_nearmiss_log --format=json`) or a throwaway admin-ajax dump during the tuning window. A proper settings-page viewer can be added later if it proves useful ongoing.

## 7. Response contract change (backward compatible)

| Field | Tier 0 | Tier 1 (fresh) | Tier 1 (followup) | Tier 2 (LLM) |
|-------|--------|----------------|--------------------|--------------|
| `reply` | ✅ | ✅ | ✅ | ✅ |
| `source` | `static` | `knowledge` | `knowledge_followup` | `llm` |
| `score` | — | ✅ | — | — |
| `_tier1_type` / `_tier1_payload` | — | ✅ (echoed back in next request's `history`) | ✅ | — |

The existing JS (`ai-chat-bot.js`) only reads `reply` today — nothing breaks. The `_tier1_*` fields are new and only need the JS to store-and-echo them in the `history` array already being sent per HO-002 Section 15; no rendering logic changes required for this handover to ship. Surfacing `source` visually (e.g. a small "from my portfolio" vs "AI-generated" tag under bot messages) is an optional follow-on, not required for this fix.
