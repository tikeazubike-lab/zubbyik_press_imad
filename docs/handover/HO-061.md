## 2. Source of Truth

Treat the existing codebase and HO-060 as the authoritative sources for the current system.

HO-060 established that the production system is:

1. A classic WordPress PHP theme (`malachy-portfolio`) with no SPA/build framework.
2. A FastAPI automation service (`imad-automation`) backed by PostgreSQL.
3. An existing lead/campaign/notification funnel that must continue operating unchanged.

The existing architecture already provides reusable mechanisms for:

- dedicated WordPress page templates;
- `/api/leads`;
- the existing contact form;
- campaign attribution via `/r/{source}?campaign=`;
- `?service=` context passing;
- WhatsApp links;
- Telegram/email lead notification;
- deterministic client-side JavaScript;
- existing visual design tokens/components.

HO-060 specifically recommends a standalone `/business-checkup/` page and a deterministic MVP before introducing server-side website/email checks or AI.

Do not invent existing capabilities, services, clients, results, infrastructure, or analytics.

## 3. Non-Negotiable Constraints

### Production safety

The current production funnel must remain functional.

Do **not** change:

- `/r/{source}` contract;
- existing campaign redirect behaviour;
- existing `contact.js` dual-submit contract;
- existing WordPress contact handler;
- existing contact nonce/honeypot/rate limiting;
- existing hero markup or CTA swap;
- `notify.py`;
- Telegram/dead-letter handling;
- existing `leads` schema unless explicitly justified;
- homepage GSAP/ScrollTrigger pipeline;
- current idempotency implementation for the existing contact form.

### Architecture

Do not:

- introduce a new frontend framework;
- introduce a SPA;
- introduce n8n;
- introduce another backend service;
- create another lead database;
- create another notification pipeline;
- refactor unrelated technical debt;
- redesign the homepage;
- turn Business Checkup into five separate public tools.

### MVP philosophy

Prefer:

> **One visitor-facing Business Checkup with multiple diagnostic dimensions behind it.**

The visitor should not be presented with five disconnected tools.

The likely conceptual structure is:

```text
Business Checkup
├── Business Health
├── Website Health       [future]
├── Email / Deliverability [future]
├── WhatsApp Readiness
└── AI Action Plan        [future]
```

For the initial MVP, determine whether **Business Health + WhatsApp Readiness** is sufficient, as recommended by HO-060.

## 4. Primary Objective

Design the smallest useful Business Checkup that can:

1. attract a visitor;
2. ask a small number of meaningful questions;
3. produce a credible, understandable result;
4. identify the visitor's likely business problem;
5. provide a clear next action;
6. hand the visitor into the existing IMAD lead/contact funnel;
7. preserve campaign attribution where available;
8. avoid making the homepage more crowded.

The checkup should feel like a useful diagnostic rather than a disguised contact form.
