## 3. Fix path — check account boundary first, don't jump to a permanent workaround

**Do this first, before either of your two proposed options:** log into
the Cloudflare dashboard and check whether `imadconsulting.co.uk` and
`zubbystudio.site` are both listed as zones under the same account. This
is faster than either of your two proposed code paths and determines
which one is actually correct.

### If same account (likely fix — try this first)

Edit the existing API token (Cloudflare dashboard → My Profile → API
Tokens) and add `imadconsulting.co.uk` to its Zone Resources, granting
`Zone:DNS:Edit` + `Zone:Zone:Read` for that zone specifically. **No
`traefik.yml` change needed** — a single Cloudflare DNS-01 certresolver
can manage multiple zones as long as the one token has access to all of
them. This is simpler than your Option 1 (second certresolver) and avoids
adding a permanent host-specific special case to the Traefik config that
someone has to remember exists a year from now.

### If different accounts — then, and only then, your Option 1

A second certresolver with a second token scoped to the other account is
the right call here, not the HTTP-01 workaround (Option 2) — DNS-01 also
means you're not depending on port 80 reachability or the Cloudflare
proxy setting for this hostname, which is a real advantage worth keeping
if the only obstacle is account boundaries rather than a technical
limitation. Moving the domain into the same account is also an option but
is Malachy's call, not a technical requirement — mention it as available,
don't push for it.

### Don't use Option 2 (HTTP-01 workaround) unless both of the above are ruled out

It works regardless of account boundaries, but only if port 80 is
reachable *and* the `api.imadconsulting.co.uk` DNS record isn't
Cloudflare-proxied (orange cloud) — both unverified right now, and it
trades one dependency (cross-account CF token) for two new ones you'd
have to maintain instead. Keep it as the fallback, not the first move.
